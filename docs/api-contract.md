# ORA DE NUIT REST API contract

**Version:** `v1` · **Base URL:** `https://{host}/api/v1` · **Format:** JSON over HTTPS

This is a design contract only. It defines the API to be implemented later; it does not add endpoints to the current application.

## Conventions

### Headers

| Header                                 | Required                          | Use                                                      |
| -------------------------------------- | --------------------------------- | -------------------------------------------------------- |
| `Accept: application/json`             | Yes                               | Expected response media type.                            |
| `Content-Type: application/json`       | For JSON request bodies           | Request media type.                                      |
| `Authorization: Bearer <access-token>` | Admin/future protected routes     | JWT access token.                                        |
| `Idempotency-Key: <UUID>`              | Reservation creation, recommended | Prevents duplicate booking creation from mobile retries. |
| `X-Request-Id: <UUID>`                 | Optional                          | Client correlation ID; echoed/generated by the server.   |

All times are ISO-8601 UTC strings. Reservation `date` is `YYYY-MM-DD`, and `time` is local restaurant time in `HH:mm` 24-hour format. IDs are serialized as strings because database IDs are `BIGINT`.

### Response envelopes

Success:

```json
{
  "success": true,
  "message": "Human-readable result",
  "data": {},
  "meta": {}
}
```

Error:

```json
{
  "success": false,
  "message": "Validation failed",
  "code": "VALIDATION_ERROR",
  "errors": [{ "field": "guestEmail", "message": "Must be a valid email address." }],
  "requestId": "0f1b4a57-0a7c-492b-9429-f2b2c3678d9b"
}
```

List responses include `meta`: `{ "page": 1, "limit": 20, "total": 42, "totalPages": 3 }`. Defaults: `page=1`, `limit=20`; maximum `limit=100`. Unknown request properties are rejected.

### Standard status and error codes

| Status | Code               | Meaning                                                      |
| ------ | ------------------ | ------------------------------------------------------------ |
| 200    | —                  | Successful read or update.                                   |
| 201    | —                  | Resource created.                                            |
| 204    | —                  | Successful deletion; no body.                                |
| 400    | `BAD_REQUEST`      | Invalid syntax or unsupported query parameter.               |
| 401    | `UNAUTHENTICATED`  | Missing, expired, invalid, or revoked JWT.                   |
| 403    | `FORBIDDEN`        | Authenticated actor lacks required role.                     |
| 404    | `NOT_FOUND`        | Resource does not exist or is soft-deleted.                  |
| 409    | `CONFLICT`         | Duplicate unique field, stale version, or booking collision. |
| 422    | `VALIDATION_ERROR` | Semantically invalid request fields.                         |
| 429    | `RATE_LIMITED`     | Client has exceeded a rate limit.                            |
| 500    | `INTERNAL_ERROR`   | Unexpected server failure; details are never exposed.        |

`400`, `401`, `403`, `404`, `409`, `422`, `429`, and `500` use the standard error envelope above. All admin mutations write an `audit_logs` record.

### Access levels

- **Public:** available to the Flutter app without an admin token.
- **Admin:** planned JWT-protected route; roles are `SUPER_ADMIN`, `ADMIN`, `MANAGER`, `EDITOR`.
- **Future auth:** documented now but intentionally not implemented until approval.

## Reservations

### `POST /reservations` — Public

Headers: standard JSON headers; `Idempotency-Key` strongly recommended.

Request:

```json
{
  "guestName": "Aisha Khan",
  "guestEmail": "aisha@example.com",
  "guestPhone": "+923001234567",
  "date": "2026-08-08",
  "time": "20:00",
  "partySize": 4,
  "occasion": "Anniversary",
  "specialRequests": "Window table if available"
}
```

Validation: name 2–120 chars; email valid/max 191; phone E.164-like/max 32; date today or later; time valid `HH:mm`; party size integer 1–20; occasion max 80; special requests max 5,000. Availability policy is evaluated server-side.

Success `201`: `data` is `{ id, confirmationCode, status: "PENDING", guestName, date, time, partySize, createdAt }`.

Errors: `409` when the requested slot cannot be accommodated; `422` field/policy validation; `429` rate limit; standard errors otherwise.

### `POST /reservations/lookup` — Public

Purpose: securely retrieve a guest’s reservation without exposing bookings to anyone who guesses a confirmation code.

Request: `{ "confirmationCode": "ON-AB12CD34", "guestEmail": "aisha@example.com" }`.

Validation: confirmation code 6–32 uppercase letters/numbers/hyphens; valid email.

Success `200`: reservation read model: `{ id, confirmationCode, status, date, time, partySize, occasion, specialRequests, cancelledAt, createdAt }`.

Errors: `404` for an unknown or non-matching pair; `422`, `429`.

### `POST /reservations/{confirmationCode}/cancellation` — Public

Request: `{ "guestEmail": "aisha@example.com", "reason": "Travel change" }`.

Validation: code format as above; email valid; reason max 500. Only `PENDING` or `CONFIRMED` reservations inside the configured cancellation window may be cancelled.

Success `200`: updated reservation read model with `status: "CANCELLED"` and `cancelledAt`.

Errors: `404` non-matching reservation; `409` reservation no longer cancellable; `422`, `429`.

### `GET /admin/reservations` — Admin (`MANAGER`, `ADMIN`, `SUPER_ADMIN`)

Query: `page`, `limit`, `status`, `dateFrom`, `dateTo`, `guestEmail`, `guestPhone`, `sort` (`reservationDate`, `reservationTime`, `createdAt`), `order` (`asc`, `desc`).

Validation: valid enum status; ISO dates; `dateFrom <= dateTo`; valid email/phone when supplied; pagination limits above.

Success `200`: paginated reservation read models including all guest/contact and operational fields. Errors: `400`, `401`, `403`, `422`.

### `GET /reservations/{id}` — Public MVP route

Validation: positive integer-string ID. Success `200`: full reservation. Errors: `401`, `403`, `404`, `422`.

### `PATCH /admin/reservations/{id}/status` — Admin (`MANAGER`, `ADMIN`, `SUPER_ADMIN`)

Request permits only `{ "status", "occasion", "specialRequests", "cancellationNote" }`.

Validation: valid lifecycle transition; occasion max 80; requests max 5,000; cancellation note max 500. A `CANCELLED` status requires cancellation metadata. Reservation date/time or party size changes require a future rescheduling endpoint with a new availability check.

Success `200`: updated full reservation. Errors: `401`, `403`, `404`, `409`, `422`.

## API behavior rules

- All deletes for gallery, banners, about, contacts, social media, pages, and admin users are soft deletes. Public endpoints never return them.
- An `EDITOR` can manage content but cannot delete it, manage settings, reservations, users, or audit logs.
- Every successful mutation returns an `ETag` derived from `updatedAt`; clients may send `If-Match` for optimistic concurrency. A mismatch returns `409 CONFLICT`.
- `Idempotency-Key` records must retain a request hash and response for at least 24 hours. This requires a future persistence table not in the current schema.
- Rate limits: public reservation create/lookup/cancel endpoints are IP and identity limited; authentication endpoints are account and IP limited. Exact thresholds are deployment configuration, not client-controlled.
